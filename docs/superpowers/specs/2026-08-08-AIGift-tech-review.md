## 方案概述

AIGift 是一款基于 AI 的微信小程序礼物推荐助手。后端采用微信云开发（CloudBase）单云函数 + 内部路由架构，与已有项目 fixbill 共用云环境、靠 `aigift_` 前缀隔离；前端为原生微信小程序，最大化复用 fixbill 的云开发骨架与表单/状态管理模式。整体方案在业务规模匹配度、复用策略和落地可行性上表现良好，但在额度一致性、伪事务风险、激励视频防刷等关键链路上存在需修复的设计缺陷。

---

## 一、方案亮点

1. **复用策略务实高效**：后端和前端均清晰列出了"直接复用 / 新增 / 调整 / 砍掉"四象限，fixbill 验证过的 `cloud.js` 单例 + env-sharing、`api.js` 统一解包、globalData 脏标记刷新、表单 `data-field` 统一输入模式被系统性地复用，显著降低实现与运维成本。

2. **额度扣减的原子性设计正确**：后端用 `UPDATE ... WHERE free_quota >= 1` 单语句条件更新实现"检查+扣减"原子化，绕开了 CloudBase `$runSQLRaw` 不支持真事务的限制，这是本方案最关键的正确决策之一。

3. **AI 层的 Provider 抽象 + 兜底策略合理**：`RecommendationProvider` 基类 + 工厂模式预留了多模型切换能力（DeepSeek/OpenAI/Qwen），重试 1 次 → 静态兜底的降级链路符合 PRD §8.4 要求，且 `is_fallback` 字段为后续质量分析提供了数据基础。

4. **数据模型设计周到**：`recommendation_items` 拆表使采纳率可直接 SQL 聚合、`recipient_snapshot` 快照保证历史复现、`invitee_openid` UQ 天然幂等——这三个设计决策都有明确的业务和技术依据。

5. **前后端 API 契约对齐**：后端提供了完整的 route→入参→返回清单，前端各页面可直接据此编码，减少了前后端协作摩擦。

6. **已知限制诚实透明**：两份文档均在末尾设立"已知限制与遗留决策"章节，明确标注了伪事务、激励视频篡改、订阅消息年度授权等风险，这比"假装没问题"要专业得多。

## 二、严重问题（必须修复）

### S1（P0）— 额度扣减与流水写入之间存在一致性窗口

**影响范围**: 额度对账准确性、用户信任

**问题描述**: 后端的 `consumeQuota` 先执行 `UPDATE users SET free_quota = free_quota - 1`（原子成功），随后 `SELECT` 读新余额，最后 `INSERT quota_logs`。若云函数在 UPDATE 成功后、INSERT 前崩溃（CloudBase 冷启动/超时/OOM），则用户额度已扣但无流水记录，对账时 `SUM(amount) != free_quota`。同理 `refundQuota` 也有此问题。

**建议方案**:
- **方案 A（推荐）**：将扣减和流水 INSERT 放在同一个伪事务的 `transaction(cb)` 内串行执行，虽然不是 ACID 但"语句串行 + 抛错中止"已足够覆盖崩溃场景——若 INSERT 失败则整批中止、可通过对账巡检补偿。
- **方案 B**：接受不一致但增加一个补偿机制（定时巡检任务对比 `free_quota` 与 `SUM(amount)` 并自动修复）。后端设计提到了对账巡检但未设计实现，应补上。

---

### S2（P0）— recommend/generate 的多表写入伪事务可能导致数据半成品

**影响范围**: 推荐数据完整性

**问题描述**: 后端 `recommend/generate` step 7 用 `transaction(async (tx) => { INSERT recommendations; for (item) INSERT items })`，但后端明确说 CloudBase `$runSQLRaw` **不支持真事务**，fixbill 的 `transaction(cb)` 是伪事务（commit/rollback 为空函数）。这意味着如果 items 循环中某条 INSERT 失败，前面的 recommendations 和 items 已写入但后续 items 丢失，产生"推荐记录存在但只有 2/5 条建议"的半成品。

**建议方案**: 在 items 循环中收集所有 INSERT 结果，若任一失败则记录告警日志并标记该 recommendation 为异常状态（`is_fallback=2` 或新增 `status` 列）；或改为先在内存中拼好全部 items 的 VALUES 子句，用单条批量 INSERT（`INSERT INTO ... VALUES (...),(...),(...)`）减少多次写入的中断风险。

---

### S3（P0）— 激励视频奖励可被客户端伪造刷量

**影响范围**: 商业模式安全、广告变现

**问题描述**: 前端的 `watchRewardVideo` 仅在 `onClose({isEnded})` 为 true 时回调后端 `quota/rewardVideoCallback`；后端也明确说明"MVP 用客户端上报 + 每日上限"。攻击者可直接调用 `wx.cloud.callFunction` 构造 `quota/rewardVideoCallback` 请求，无需观看任何视频即可每日白嫖 15 次（5 轮 × 3 次/轮）推荐额度。对于一个**以额度为核心变现杠杆**的产品，这将直接导致广告收入归零。

**建议方案**: 微信小程序激励视频支持**服务端回调**。MVP 应接入此回调。实现路径：

1. 在 CloudBase 控制台开启云函数 HTTP 访问
2. 新增路由 `quota/rewardVideoServerCallback`（加入 PUBLIC_ROUTES，靠签名校验而非 openid 鉴权）
3. 前端 `onClose` 仅做 UI 跳转，额度发放由服务端回调驱动

或至少将激励视频每日上限从 5 降至 2-3，并加 IP/openid 频率异常检测。

---

### S4（P1）— 限流实现有 N+1 查询且粒度不足

**影响范围**: 性能、防刷

**问题描述**: 后端的限流方案是"查 `aigift_recommendations` 最近一条 `created_at`"来判断距上次 generate < 5s。这要求每次 generate 多一次 SELECT 查询，且仅限制了 `recommend/generate` 一个路由。但 `recommend/regenerate`、`quota/rewardVideoCallback`、`recipient/create` 等写入路由完全没有限流。

**建议方案**: 引入基于 openid 的通用限流中间件（内存计数器或 Redis-like），覆盖所有写入路由；至少对 `recommend/generate`、`recommend/regenerate`、`quota/rewardVideoCallback` 加限。

## 三、改进建议（建议优化）

| # | 问题描述 | 建议方案 | 优先级 |

| I1 | **共用 CloudBase 环境的资源争抢风险量化不足**：PRD §14 提到"必要时迁移独立环境"，但未给出触发迁移的具体指标（如 P95 > X 秒、错误率 > Y%）。fixbill 和 AIGift 共用同一 MySQL 实例，连接数、CPU、IO 都是共享的。 | 建议在部署 checklist 中增加监控告警项：CloudBase MySQL 慢查询数、连接池利用率、云函数冷启动时间、并发数；定义明确的迁移触发条件（如"连续 3 天 P95 > 10s"或"MySQL 连接池利用率 > 80%"）。 | P2 |
| I2 | **AI 调用超时 7s 设置偏激进**：加上 CloudBase 冷启动（可能 1-3s）、DB 查询、内容安全检测、落库等开销，整体 P95 < 8s 的目标非常紧张。若 AI 首次调用超 7s → 重试再 7s → 兜底执行，极端情况可能超 15s。 | 建议将 AI 单次超时设为 8-10s 并去掉重试（或重试超时设 5s），或调整 P95 目标到 12s 以留出余量。 | P2 |

## 四、微信小程序架构视角补充评审

### 4.1 前端架构与 PRD §6 页面设计对齐性

**结论：基本对齐，有 2 处需注意的差异。**

PRD §6.2 中 7 个页面（推荐首页、推荐结果、对象列表、对象编辑、对象详情、历史、我的）在前端设计中均有对应的 `pages/` 目录，完全对齐。

**差异 1（🟡 低风险）**：PRD §6.3 提到「我的」页面包含"设置（隐私/关于/反馈）"，但前端设计仅一行带过，未明确设置项的页面结构——是 profile 页内展开还是独立 `pages/settings` 跳转页。建议：若设置项少于 5 条可 profile 内嵌；隐私协议需跳 `web-view` 或独立页面。

**差异 2（🟡 低风险）**：PRD §6.3 结果页提到"分享卡片得次数"作为底部操作之一，但分享奖励的后端触发路径是 `share/inviteCallback`（被邀请者首入触发），而非分享者主动触发。**分享者点击"分享"按钮后无法立即获得额度到账反馈**——额度仅在好友打开小程序后才发放。前端应在按钮旁加说明文案"好友打开后自动到账"，避免用户期待即时反馈。

---

### 4.2 微信生态能力对接技术可行性

#### wx.login 授权（✅ 可行）

`autoLogin` 流程正确。**补充**：CloudBase 环境下 `wx.cloud.callFunction` 的 `event` 中已自带 `wxContext.OPENIP`，因此 `user/autoLogin` 可直接从 `wxContext` 取 `openid`，不一定需要前端传 `loginCode` 再后端 `code2session`。建议确认 `loginCode` 参数是否冗余。

#### 订阅消息（✅ 可行，需注意配额机制）

- 礼物提醒场景只能用**一次性订阅**（长期订阅仅限政务、医疗等特定类目），每次用户授权 = 1 条发送配额。
- **循环提醒的次年授权问题**：需设计一个**待授权队列**——检测到有 `notified_year < 当前年` 且 `is_recurring=1` 的记录时，在 App `onShow` 时弹起 `requestSubscribeMessage`。前端设计未描述此队列机制，建议补充。

#### 流量主广告（✅ 可行）

- **流量主准入条件**：小程序需满足"累计独立访客（UV）≥ 1000"才能开通流量主。MVP 上线初期可能不满足此条件，建议 `ad-slot` 组件内部做**降级处理**——广告实例 `onError` 时隐藏广告容器。
- **激励视频预加载**：建议在页面 `onLoad` 时即创建实例并 `load()`，用户点击时直接 `show()`，减少等待时间。

#### 激励视频回调（🟡 存在安全隐患——同 S3）

微信小程序激励视频的**服务端回调**需要在小程序管理后台「流量主」→「广告位管理」中配置回调 URL（HTTPS），微信会在用户看完视频后向该 URL 推送签名的回调消息。CloudBase 云函数可通过 HTTP 访问实现：

```
微信广告服务端 → POST https://tcb-api.cloud.tencent.com/.../http/aigift_app
                 data: { route: 'quota/rewardVideoServerCallback', adUnitId, openid, isEnded, signature, ... }
```

### 4.3 云函数模块划分覆盖度

**结论：模块划分合理，但有 2 处覆盖缺口。**

PRD 全部功能需求与后端模块逐一对照均覆盖。缺口：

1. **`history/list` 模块归属未明确**（同 I9）
2. **用户数据删除接口缺失**（同 I6），建议 MVP 即实现

**模块拆分合理性评价**：8 个模块的粒度适中。新增的 `ai/` 抽象层是一个亮点——将 AI 调用与业务逻辑解耦，未来切换模型或做 A/B 测试时不需改 `recommend/` handler。

---

### 4.4 共用 CloudBase 环境的隔离策略潜在冲突

表名/函数名/触发器名/环境变量前缀隔离方案有效。需关注的共享资源：

| 资源 | 冲突风险 | 说明 |
|------|---------|------|
| MySQL 实例 | 🟡 P2 | 连接数、CPU、IO 共享。`aigift_db_keepalive` 每 20 分钟执行，若 fixbill 也有类似机制可能叠加。建议确认 fixbill 是否已有 keepalive，有则复用。 |
| 云函数并发配额 | 🟢 P3 | 共享同一环境并发限制（通常 1000）。MVP 阶段流量小，风险低。 |
| **微信 API `access_token`** | 🟡 P2 | 如果 AIGift 和 fixbill 是不同 AppID，各自需独立 `access_token`，但共享同一组环境变量。若 fixbill 也用 `WX_MINI_APPID` 换 token，两个项目变量会**互相覆盖**。需确认：独立 AppID 时环境变量需加 `AIGIFT_` 前缀隔离。 |

## 五、待确认事项

1. **AIGift 是否有独立 AppID？** 若挂 fixbill 同主体则需简化 `cloud.js`，若独立则需 CloudBase 控制台配置环境共享——两种路径的技术细节不同。建议尽早定论。

2. **DeepSeek API 的 `response_format: { type: 'json_object' }` 是否可靠？** 建议在实际编码前先用 DeepSeek API 做一次 POC，验证 JSON 模式的稳定性和输出格式遵从度。

3. **定时触发器 cron `0 0 9 * * * *` 的时区**：CloudBase 定时触发器的 7 段 cron 使用的是 UTC 还是北京时间？若是 UTC，则 `0 0 9` 对应北京时间 17:00，提醒推送时间会错误。

4. **CloudBase Node SDK 版本与 `$runSQLRaw` 的当前行为**：建议确认当前 SDK 版本是否有更新（是否已支持事务），这会影响 S1/S2 的修复方案选择。

5. **微信订阅消息模板的字段要求**：`buildReminderData(d)` 需按模板字段填充，但模板尚未在微信公众平台创建。建议提前创建模板并确认字段格式。

6. **fixbill 是否已有 DB keepalive 触发器**：若有则 AIGift 可复用同一个，不需要单独建 `aigift_db_keepalive`。
